# 叙演工坊：产品需求与交互设计

版本：0.2-draft · 日期：2026-09-18  
适用对象：产品设计、前后端开发、Agent开发、测试及后续接手开发的AI助手。

## 1. 产品定义

叙演工坊是一个以世界资料为依据、以人物动机为驱动、以可追溯分支为产出的剧情推演工作台。用户既可以从已有小说建立世界，也可以手工设计世界或导入世界模板；随后把原创人物或已有角色放入特定时间与事件，观察人物选择如何改变关系和后续剧情。

产品的核心资产是可编辑、可追溯的世界资料与剧情状态。对话、地图、时间线和小说草稿都建立在这些资产上，避免资料分散在多个聊天窗口中。

### 1.1 用户与价值

| 用户 | 典型问题 | 产品提供的结果 |
|---|---|---|
| 网络小说作者 | 设定多、伏笔多，人物容易忘记经历或性格漂移 | 有来源的设定库、人物记忆、事件链和连续性检查 |
| 游戏剧情编剧 | 多角色、多路线、不同任务选择难以比较 | 条件事件、人物互动、分支对照与结构化导出 |
| 世界观创作者 | 地理、势力、资源与历史之间缺少联系 | 关联编辑的世界百科、地图、势力及时间线 |
| 原创角色创作者 | 想观察同一角色在不同世界里的表现 | 可复用人物卡、入场适配、跨世界实例 |

### 1.2 最重要的成功体验

作者导入一部小说，校对关键人物和规则，选择“某次谈判前一天”，让一个自创人物加入。两名原著人物和新人物由不同模型扮演，各自只知道自己应当知道的事。系统记录行动、裁定结果、关系变化与关键分歧。作者可以退回第五回合，改一句话再走一条分支，最终把满意的场景导出为素材或正文草稿。

## 3. 产品原则

1. **作者拥有最终解释权。** 自动提取与模型补全先进入候选区；作者确认后才成为世界版本的一部分。
2. **事实有出处。** 原文事实关联章节和文本位置；推断与创作补充明确标记。
3. **世界、角色、时间与分支一起决定上下文。** 不把所有资料无差别塞给每个角色。
4. **角色提出行动，系统决定结果。** “我杀死对手”首先是一项尝试，而不是直接生效的事实。
5. **资料可携带。** 世界和人物使用版本化开放格式，不把用户锁在单一模型厂商。
6. **过程可暂停、可恢复、可比较。** 已提交回合可以重放，未知状态的请求不能偷偷重复计费。
7. **跨平台差异显式处理。** Windows先交付，不把Windows路径、系统命令或后台常驻假设写入领域规则。

P0：Windows首个可用版必需。P1：Windows增强及其他平台主要能力。P2：成熟期扩展。

| 世界地图 | 地点层级、相邻/行程关系、导入底图并标点 | 区域、路线、历史势力范围 | 辅助生成地图图片、地形编辑 |
| 时间与事件 | 故事时间、章节顺序、事件前后关系、事件列表 | 因果图、条件事件、复杂历法 | 宏观历史推演 |
| 人物卡 | 通用卡、世界实例、入场适配、记忆、目标 | 阶段成长、细化能力体系 | 可分享卡组与风格包 |

## 5. 关键业务对象

### 5.1 工作区、世界、版本、分支

- 工作区：一个创作项目，可包含多个相关世界和共享人物库。
- 世界：世界观及其人物、地点、势力、规则、历史等资料集合。
- 世界版本：作者审定的资料快照；已被推演引用的版本不可原地覆盖。
- 分支：基于某个世界版本、时间锚点和状态快照产生的独立剧情路线。
- 推演会话：在一条分支上执行的一次有明确目标和预算的运行。

资料修改形成新修订。旧推演保持原来引用；采用新设定时创建新分支或显式升级，并展示差异。

### 5.2 世界规则

规则分为硬约束与叙事倾向，并有适用范围、来源和例外条件。

例如“此区域无法使用传送术”是可检验的硬约束；“贵族通常不公开道歉”是叙事倾向。叙事倾向不应被当作系统必然结果，否则人物无法做出有意义的选择。

规则类型至少覆盖：自然/超自然规律、能力与代价、社会制度、资源约束、地理通行、身份限制、叙事锚点。首版机器可执行规则只开放白名单条件表达式，不执行世界模板携带的代码。

### 5.3 通用条目字段

所有条目至少包含：稳定ID、所属世界、类型、名称、别名、说明、标签、结构化属性、来源、审核状态、有效时间、修订号、关联条目。

证据性质分别记录为：原文明确记载、原文中的说法/传闻、模型推断、作者设定、推演结果。审核状态另设为候选、接受、拒绝、待解决冲突。二者不可混成一个“可信/不可信”开关。

### 5.4 世界地图

支持三种表达：地点树、拓扑地图、图片底图。无地理坐标时，优先表达“青石镇位于都城以北，骑马约两天”，不杜撰经纬度。

地点字段包括：父地点、类别、环境、控制势力、出入口、邻接地点、行程区间、危险、资源和时间有效范围。底图坐标属于图像标注，不能直接当成真实距离。

模型补全的地图位置用不同样式显示；原文没有证据的路线必须标“假设”。地图绘制工具与剧情事实库分开：一张漂亮地图不能自动证明世界中的距离与边界。

### 5.5 时间线与事件线

时间线回答“何时发生”，事件线回答“为什么发生、依赖什么、导致什么”。两者共享事件ID，但分别提供时间视图与因果视图。

事件支持：精确日期、日期区间、相对时间、只知道先后顺序、未知时间。记录原文章节出现位置，避免把倒叙章节误当作事件发生顺序。

事件字段包括：参与者、地点、触发条件、前置事件、目标、过程、结果、状态变化、原著结果、锁定策略、来源。未来原著事件进入“待发生事件候选”，分支改变前提后重新判断，不能机械重演。

### 5.6 势力与关系

势力包含使命、公开目标、隐秘目标、制度、层级、成员、领地、资源、盟友、敌人及内部派系。角色身份必须有生效时间，避免“未来加入组织”的信息提前出现。

人物关系和势力关系都是有方向、有时间的边。例如A信任B不代表B信任A。“亲属/师徒/盟约”是关系类型；信任、恐惧、好感、债务等是可选维度。数字只用于相对变化，默认不宣称具有心理学精确性。

同时记录公开关系、实际关系和某人物以为的关系。幕后同盟不能自动成为所有人都知道的事实。

### 5.7 重要物品及其他剧情要素

物品记录来源、当前持有人、位置、能力、使用条件、消耗、限制、唯一性、已知/未知属性及转移历史。转移需要同时验证原持有人与接收人状态。

线索、秘密、伏笔、承诺、契约、任务、伤势、资源和期限均作为可引用对象或状态。秘密应定义“谁知道、何时知道、通过什么渠道知道”；伏笔应区分作者标记、原文已披露和人物实际掌握。

## 6. 小说导入与世界构建

### 6.1 导入向导

1. 选择文件并保留原始内容副本；检查编码、章节、重复内容与体量。
2. 预览章节切分并允许修正，选择全文/章节范围。
3. 选择提取范围、模型、预算、是否允许向外部模型发送所选片段。
4. 可先对少量章节抽样，展示质量、token消耗和全书成本估算区间。
5. 后台逐步提取，显示已处理章节、失败项、待校对项和已用预算。
6. 作者校对候选条目与冲突，提交第一个世界版本。

提取不应把小说一次性发送给模型。详细流水线见技术文档。全文可先建索引，用户选择的人物与章节优先形成可用结果，避免等待整本书处理结束才能开始编辑。

### 6.2 校对中心

采用“左侧候选/冲突列表—中间结构化资料—右侧原文证据”的布局。允许按人物、章节、证据类型和风险筛选。

支持接受、修改后接受、拒绝、保留多个说法、合并同一实体、拆分误合并实体。合并与拆分必须更新引用且可追溯；同名人物不得仅凭名字自动合并。

模型置信度只作为辅助排序，不当作已校准概率。界面优先显示证据是否齐全、是否被多处支持、是否存在矛盾。

### 6.3 缺失信息

区分未知、不适用与确定不存在。原文未说明人物年龄时保持未知；用户可要求创作补全，但补全内容必须标记为作者采纳的新增设定。

## 7. 世界模板

### 7.1 创建方式

- 空白世界：逐步填写类型、基调、规则、时代、地点和角色。
- 向导创建：模型针对缺失项提出问题与候选方案，由作者选择。
- 模板导入：校验格式、版本、依赖、来源信息与文件摘要，再创建新世界或显式合并。
- 世界导出：作者选择版本及内容，可排除正文、私密设定或推演记录。

### 7.2 模板层级

“世界蓝图”只包含世界结构与规则；“历史快照”包含特定时间的完整状态；“开场情境”包含地点、人物、事件与开场条件。三者不能含糊地合并成一个模板开关。

模板必须说明所处历史时间及是否含未来剧透。世界规则字段支持命名空间扩展，例如 `x-xuyan-fantasy.meridians`；未知扩展保留但不执行。

### 7.3 兼容与分享

P0保证本项目JSON/ZIP格式的导入导出。第三方人物卡、世界书和其他软件模板在P1逐个编写适配器；不能承诺任意他人格式无损兼容。导入时展示字段映射、丢失字段和不兼容行为。

署名、来源和使用说明保留在包中；是否上传或公开分享由用户明确操作。模板内容作为资料读取，不授予联网、命令执行或访问API Key的能力。

## 8. 人物卡与跨世界投放

### 8.1 通用人物卡

建议字段：姓名/别名、身份概述、外貌、性格倾向、价值观、底线、长期目标、短期目标、恐惧、秘密、说话方式、典型台词、能力描述、能力代价、弱点、初始装备、关键经历、关系原型。

字段分成“核心身份”“可适配内容”“作者私密说明”。例如忠诚观念可作为核心身份，魔法种类可适配，但模型绑定属于运行配置，不写死在可移植人物卡里。

人物卡需允许矛盾与成长：一个人可以勇敢但害怕失去家人，也可以在重大事件后改变目标。系统记录变化依据，不把所有特征固定成不可改变的标签。

### 8.2 世界人物实例

通用卡投放后产生独立实例，记录所属世界/分支、身份、入场时间地点、能力映射、装备、资源、伤势、记忆、当前目标与关系。不同世界中的同一人物互不共享记忆；只有用户主动建立跨世界经历迁移时才携带。

更新通用卡不会自动改写已有实例。可以比较新旧卡后选择性应用并创建修订；正在运行的会话仍使用已固定的版本。

### 8.3 入场向导

1. 选择人物卡及版本。
2. 选择世界版本、时间锚点、地点和目标事件。
3. 选择入场模式：本土身份、外来者/穿越者、访客观察模式。
4. 选择知识策略：只知道自身经历、获得背景常识、携带指定剧透。默认不提供原著未来信息。
5. 适配能力、语言、装备、资源和社会身份。
6. 检查冲突并展示“保留/削弱/替换/封印/待确认”清单。
7. 确认初始关系与初始状态，创建分支并入场。

能力适配以语义、范围、代价和目标世界规则为准，不用跨世界通用战力数值强行换算。例如“随意传送”在无空间魔法的世界中需要被封印、转为技术能力或作为明确例外；不能静默变成可用技能。

### 8.4 三种历史模式

| 模式 | 行为 | 遇到冲突 |
|---|---|---|
| 原著约束 | 维护作者选定的关键锚点，探索细节变化 | 不强制人物做违背动机的事；不可同时满足时暂停并解释冲突 |
| 分支推演（暂定默认） | 从入场点另开历史，保留原著供比较 | 前提改变时取消或改写后续候选事件 |
| 自由沙盒 | 可修改更多世界规则并探索大幅变化 | 仍需维护当前已选规则的一致性；修改规则生成新修订 |

## 9. 多模型人物推演

### 9.1 Agent职责

| 角色 | 输入 | 输出 | 权限 |
|---|---|---|---|
| 资料整理者 | 原文片段、实体索引 | 候选条目、证据与冲突 | 提交候选，无权直接覆盖资料 |
| 场景主持 | 当前场景状态与公开目标 | 场景描写、发言顺序建议 | 无权泄露角色私密信息 |
| 人物扮演者 | 人物可见状态、记忆、目标 | 发言、行动意图、公开理由 | 只控制自己，不能裁定他人结果 |
| 规则裁判 | 行动意图、规则、真实局部状态 | 候选结果与状态变更 | 结果经过确定性校验才提交 |
| 连续性检查者 | 已发生记录、约束与候选变化 | 矛盾、风险、修复建议 | 不直接改写历史 |
| 创作整理者 | 已接受的事件与对话 | 摘要、大纲、场景草稿 | 只输出衍生作品 |

这些是逻辑角色，不要求每个角色都常驻一个模型进程。简单场景可合并主持与叙述，确定性规则优先由代码检查。首版不采用无限循环的自主Agent。

### 9.2 运行单位

一个回合是一批基于同一状态快照提出的行动，以及一次经校验的状态提交。多人同时行动时，彼此不能读取尚未公开的意图。顺序对话时，每名角色发言后形成新的可见上下文。

首版默认为顺序场景互动，2—4名活跃人物、最多20回合，可手动调整。并发提案模式在引擎中预留，但完整冲突仲裁作为后续增强，避免首版同时实现过多调度策略。

### 9.3 导演控制

作者可以暂停、单步、停止、指定发言者、给某人物私下指令、添加公开事件、调整外部条件，或回到检查点开新分支。干预记录显示在时间线上，并标记其作用范围。

直接控制人物时，可编辑角色的拟议发言/行动后提交。更改已提交回合的行为应创建分支，不能悄悄抹掉历史。

### 9.4 停止条件

达到回合数、场景目标完成、预算不足、人物退出、出现无法裁定的规则冲突、连续无状态变化、用户停止、提供商持续失败时停止或暂停。无进展检测默认连续3回合触发提示，不自动为了“有戏剧性”制造战争或背叛。

### 9.5 输出内容

- 可读记录：角色对白、行动、场景叙述。
- 结构化记录：事件、物品/位置/伤势/资源/关系变化。
- 决策说明：引用的规则、证据和简短裁定依据。
- 创作启发：矛盾升级点、可延伸事件、人物是否偏离卡片设定。
- 运行信息：使用模型、耗时、token、费用估计、重试与干预。

不要求或存储模型隐藏思维链；“理由”指适合向作者展示的简短解释和证据引用。

### 9.6 角色知识边界

作者视角可以看到秘密，人物请求只能携带其可访问内容。秘密拥有者的内心记录不能混入公共场景摘要。自动摘要、检索索引、提示词缓存和分支复制都必须保留可见范围。

即使不发送未来信息，预训练模型仍可能知道知名小说。提供“匿名化推演”选项：替换作品名和实体名，按已提供事实推演；说明它降低剧透风险但不能保证模型完全忘记已有知识。检测到未经授权的未来事实时阻止该结果写入。

## 10. 分支、比较与结果采纳

每个分支保存父分支、起点回合、固定世界版本、随机参数、卡片版本和导演干预。允许在任意已提交检查点开新分支。

比较界面展示：共同起点、首个关键分歧、角色存活与位置、关系变化、物品归属、事件差异和成本。比较多个模型输出时，固定输入条件并记录差异；不能把少量生成结果解释成精确的事件发生概率。

“采纳结果”支持三个独立动作：保存为创作素材、生成正文草稿、选择性形成世界新版本。默认只保存到当前分支。正式世界版本更新需要作者选择具体变更，不自动整段覆盖。

## 11. 创作辅助

可根据已提交的推演生成对白整理、场景草稿、章节大纲、伏笔清单和连续性报告。草稿是衍生文稿，其新增内容若要成为世界事实，必须再走设定变更流程。

首版导出Markdown、纯文本和结构化JSON。专业文档排版、游戏对话系统格式、图片生成和语音配音后续扩展；这些能力不阻塞核心推演。

## 12. 界面信息架构

左侧主导航：工作台、世界库、人物库、推演室、创作稿、任务中心、设置。

世界内导航：总览、规则、人物、势力、地点/地图、时间线、事件线、物品、关系、其他条目、来源、版本。

### 12.1 关键页面

| 页面 | 主要内容 | 主要动作 |

| 工作台 | 最近项目、未完成任务、最近分支 | 新建世界、导入小说、继续推演 |

### 12.3 移动与无障碍

Android采用单栏和底部导航，重点支持阅读、轻编辑与参与短场景；地图/关系图提供列表替代。长任务需要明确前台执行限制或转交服务端。布局从首版起使用响应式组件、触控命中区、键盘焦点、非颜色唯一状态提示和可调整字号。

## 13. 平台范围

| 平台 | 首阶段定位 | 完整版本要求 |
|---|---|---|
| Windows | 首个正式交付目标 | 本地完整流程、安装升级、备份恢复 |
| macOS | 尽早编译和基础冒烟 | 本地完整流程、权限与签名验证 |
| Linux | 尽早编译和基础冒烟 | 指定发行版依赖、打包与凭据存储 |
| Web | 首版固定共享协议与视觉规范 | 独立浏览器前端＋C++服务端；账号/自托管访问边界 |
| Android | M0验证关键库；后续产品化 | 文件选择、生命周期、短任务、本地/远端模式 |

Windows、macOS、Linux和Android共享C++核心与Qt Quick组件，按平台调整布局和系统接口。正式Web版采用浏览器界面与C++服务端，共享领域逻辑、协议和视觉规范，Web界面需单独实现。Qt WebAssembly作为可选验证路径，不作为五平台交付的前提。首版不承诺纯浏览器离线完成全部推演和凭据管理。

### 13.1 C++方案的产品含义

C++承担资料处理、模型调用编排、推演状态、检索、版本和本地数据；QML承担桌面与Android的界面描述。开发者不需要编写Rust。为了浏览器体验，正式Web界面仍可使用TypeScript；“C++核心”不等于所有界面、平台桥接和构建脚本都必须用C++。

Qt组件复用不代表桌面三栏布局可以直接缩到手机。移动端以世界资料阅读、人物卡修改、短场景互动为起点，再逐步覆盖其余能力；不同平台的功能缺口列在发行矩阵中。

## 14. 模型与成本体验

模型配置分三层：提供商连接（端点与凭据）、模型能力与价格、任务/人物绑定。用户可让低成本模型做候选提取，较强模型做复杂裁判，每个人物使用不同模型；最终以测试结果判断质量。

提供“省成本、均衡、自定义”配置模板，但不硬编码长期固定的厂商排名或模型名。能力检测和手工配置共同决定是否可用。

开始任务前展示可能发送的数据范围、最大回合数、输出上限和费用估计。额度以任务级和工作区级共同限制；接近上限先停止安排新请求。取消请求不保证撤销已由厂商计费的处理。

## 15. 本地数据与隐私边界

本地优先意味着资料默认保存在本机；调用远程模型仍会发送所需片段。界面应允许查看发送范围、限制可用提供商、选择本地模型端点，并明确远程嵌入同样会发送文本。

API Key放在操作系统凭据存储或经过验证的加密保险库中，不进入世界包、日志和前端持久化存储。原始小说、人物秘密和推演内容默认不写入遥测；诊断包由用户主动生成并预览。

本地项目不是默认全盘加密。需要更高保密等级时，后续增加项目加密；不能因为保护了API Key就宣称小说文件已加密。

## 16. 首版边界与非目标

首版必须有基础地图/时间线/关系视图、模板导入、人物入场、多模型互动和可回退分支；这些是核心体验，不能全部延后。

首版暂不承担：大型多人在线世界、完整游戏物理与战斗引擎、复杂经济模拟、公开模板市场、自动抓取全网小说、语音视频角色、3D场景、训练基础模型，以及无人工校对的“百分百准确提取”。

本产品给出基于设定的合理创作可能性，不承诺预测唯一正确剧情。连续性和人物动机优先于单纯增加冲突强度。

## 17. 待用户进一步选择

以下问题不阻塞初稿，答案会影响后续实现优先级：

1. 更偏重严谨原著推演、自由互动体验，还是高质量小说草稿？
2. 常见小说长度、导入格式和一次活跃角色数量？
3. 常用模型厂商、月度费用范围、是否必须接入本地模型？
4. 是否需要离线使用、项目加密、云同步或团队协作？
5. 地图更重视地理推理、拖拽编辑，还是视觉美术效果？
6. 战斗结果希望偏叙事裁定，还是需要明确的数值/骰子规则？
7. 是否计划公开发布或收费；首批用户是否只有本人？

这些是需求选项，不需要一次全部回答。阶段验收见第三份文档，C++首轮开发起点见第四份文档。
